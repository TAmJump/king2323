# §2. 結論サマリ

### Q1: 10 億同時アクセスは物理的に困難

- 5 分で 10 億 ≒ 333M req/sec
- これは **Cloudflare 全顧客合計のピーク(5,000 万 req/sec)の 7 倍、Visa+MC 合計決済 TPS(13 万)の 2,500 倍**
- 達成には 70 億〜700 億円規模のプロジェクトと 12〜24 ヶ月の開発
- **最大の壁は決済**: どの payment provider も 33M TPS は扱えない

### Q2: 各国現地時刻ではなく、JST 23:23 一本を維持

- ブランドの核「世界が同じ瞬間に同じ画面で意志決定する儀式」と整合(session ⑥ §28-7 で確定済)
- 各国時刻に分散すると「同時性」が崩壊する
- ただし、現状サイト L3868(`ritual.why.p2`)に **JST 一本 と 各国現地時刻同期 の矛盾文** がある → session ⑦ で修正済(v20260518g)

### Q3: クイズ対策はランダム出題が必須(ただし Cycle 1 ではクイズ自体ない)

- Cycle 1 のエントリーは ¥100 + Mission 文だけ。クイズ要素なし
- THE TRIAL(3 問突破)は **Cycle 2+ の機能**(rules.html L90-92 で法務カバー済)
- Cycle 2 で実装するなら、operator 指摘どおり同一問題出題は SNS バラまきで崩壊する
- **対策**: 巨大問題プール(5,000+) + 個人別 SHA-256 抽出 + 一部反応型(知識ゼロタイプ)
- 詳細議論は本ドキュメント §6 へ

# §3. 「世界が参加できる設計」の正解

## 「参加」を 2 種類に分解

| 行為 | 必要な同期性 | 必要な技術 |
|---|---|---|
| Bell Entry を記録する(¥100 + Mission) | 非同期で OK | Cloudflare CDN + Worker + 国別決済 |
| Bell rings を見守る(儀式の瞬間に立ち会う) | 同期(JST 23:23 ぴったり) | 既に実装済み(静的 HTML + クライアント側 JS) |

混ぜていたから「10 億同時」が必要になっていた。**分けると桁違いに楽**。

## 4 層アーキテクチャ

```
[月]                                                    [金 23:23 JST]      [土 23:23 JST]
 │                                                        │                  │
 │  ◀━━━ 7 日間 Entry Window ━━━▶                       │                  │
 │  世界中どこからでも ¥100 等価で Bell Entry             │                  │
 │  各国の通貨 / 決済プロバイダで                        │                  │
 │  Mission も提出                                        │                  │
 │                                                        ▼                  ▼
 │                                              ★ Founding Bell      ★ The Three
 │                                              世界が一斉に見守る   発表
 │
 └─ 各 TZ 23:23 = Carrier Bell(地域演出)
    その地域がライトアップ、Cycle の "kingdom" 名で呼ばれる
```

| 層 | 役割 | スケール課題 | 解決 |
|---|---|---|---|
| Entry Window(7 日間) | 参加者が「いつでも」入る | 10 億人参加 → 平均 1,667 entries/sec、ピーク 1 万/sec | Cloudflare Queue + 分散書き込み + 国別決済多重化 |
| Witness Bell(JST 23:23 の 5 分間) | 世界が同時に儀式を見る | 単なる静的ページ + 時刻チェック | **既に完成**。CDN edge 配信、追加開発ゼロ |
| Carrier Bell(各 TZ 23:23 の 30 秒間) | 地域の演出ハイライト | 静的アニメだけ | クライアント側 JS が現地時刻判定して演出発火 |
| Announcement(土 23:23 JST) | The Three 発表 | コミット&リビール方式 | クライアント側 SHA-256 計算で O(1) |

これで「世界が参加する」を物理的に達成可能。同時負荷ピークは **数千 RPS**、現状の Cloudflare + Workers + D1 でほぼ余裕。

# §6. Cycle 2: THE TRIAL の不正対策

operator 提起の質問 3「SNS でクイズの答えバラまき対策」への詳細議論。

## 対策案(SNS バラまき耐性レベル別)

| 案 | 仕組み | バラまき耐性 | 実装難易度 |
|---|---|---|---|
| **A. 静的問題プール + ランダム抽出** | 1,000 問プール → 個人別 SHA-256(receipt+seed) で 3 問抽出 | 中 | 低 |
| **B. 巨大プール(10,000+ 問)** | A + プール拡大 | 高 | 中(問題作成コスト大) |
| **C. 時間限定生成** | Bell 開門 30 分前に問題プール公開、開門中のみ参加者各自に個別配布 | 超高 | 高 |
| **D. 動的素材問題** | その日の市場データ、ニュース、生成画像から機械生成 | 超高 | 超高 |
| **E. 暗算 / 反応型(知識ゼロ)** | 「5 秒以内に 3 桁計算」「画面の動く点をクリック」など | 完全 | 中 |

## 推奨

**B + C のハイブリッド + 一部 E**:
- 5,000 問程度のプールを事前構築(KINGMAKER の哲学・歴史・倫理・パターン認識)
- Bell 開門時、receipt 番号と Public Seed で決定論的にプールから 3 問抽出(検証可能性のため)
- 開門前にプール全体は公開しない
- 一部を E(反応型)にしてカンニング不可能化

## 設計の北極星

> THE TRIAL は知識テストではなく、**この 5 分間にこの場で考える人間の意思**を測るもの

このフレーズを設計の北極星にすれば、自然に「事前に答えを準備できない問題」だけが残る。

# §8. 「10 億同時」を作らない理由 — operator への提言

operator が「世界全人類が同時参加」を強く望むなら、以下の選択肢:

| アプローチ | 時間 | 予算 | リスク |
|---|---|---|---|
| **(A) 10 億同時を物理達成** | 12〜24 ヶ月 | 70〜700 億円 | 70-80% で payment 層が崩壊 |
| **(B) 段階解禁で 24 ヶ月後に世界カバー(本ドキュメント推奨)** | 24 ヶ月 | 月数十万〜数百万円 | 法務遅延のみ |

私の推奨は **(B)**。理由 3 つ:

1. 物理的に地球のインフラ容量超え
2. (A) を動かす 24 ヶ月で KINGMAKER のブランドが別軸で動かなくなる
3. (B) の方がブランド物語として深い:「自分の国の Bell はいつ?」という渇望は強いエンゲージメント

ただし operator がどうしても (A) を作りたいなら、進化的に:
- Phase 1: 現状で Cycle 1 launch(日本 1 万人想定)
- Phase 2: Cycle 5 までに 100 万同時対応(数百万円、半年)
- Phase 3: Cycle 30 までに 1,000 万同時対応(数千万円、1.5 年)
- Phase 4: 1 億同時 → ここで段階解禁の方が安いと operator が必ず気づく
